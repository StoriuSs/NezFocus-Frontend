# Internationalization (i18n)

Every word the app shows comes from a translation catalogue, in English and
Vietnamese, through [react-i18next](https://react.i18next.com/). This page is
where the catalogues are, how to use them, and how to add a language.

## Using it

```tsx
import { useTranslation } from 'react-i18next'

function MyComponent() {
    const { t } = useTranslation()             // the common namespace
    return <h1>{t('buttons.tryAgain')}</h1>
}

function SignInTitle() {
    const { t } = useTranslation('auth')       // another namespace
    return <h1>{t('signIn.title')}</h1>
}
```

From any namespace, with a prefix: `t('pages:notFound.title')`,
`t('api:USERNAME_CONFLICT')`. A component that reads several names them all,
its own first: `useTranslation(['users', 'common'])`, then `t('profile.bio')`
and `t('common:saveBar.save')`. Outside React (a toast fired from a store),
import the instance: `import i18n from '@/i18n'`, then `i18n.t('auth:…')`.

## Namespaces

| Namespace | What is in it | Example keys |
|-----------|---------|-------------|
| `common` (the default) | Shared UI: buttons, the AuthShell and AppShell (the rail, the channel list, the server settings column: `shell.*`), error screens, the settings save bar, the shared crop dialog (`imageCrop.*`) | `buttons.tryAgain`, `shell.openNav`, `saveBar.save`, `imageCrop.zoom` |
| `pages` | The pages that belong to no feature, the legal pages' bar and footer among them | `pages:notFound.title`, `pages:legal.terms` |
| `api` | A message per API error `type` | `api:AUTH_INVALID_CREDENTIALS`, `api:USERNAME_CONFLICT` |
| `auth` | Everything on the auth pages and the account page (`settings.*`) | `auth:signIn.title`, `auth:passwordRules.…`, `auth:sessionEnded.password-changed` |
| `users` | The profile page (also the display name's label, hint and errors on "complete your account"), the crop dialog's title, description and save (`crop.*`), the discard question, its toasts | `users:profile.avatar.change`, `users:validation.displayNameTooLong`, `users:toasts.profileUpdated` |
| `settings` | The Appearance & language, Notifications and Privacy pages, and the "not saved" toast. Loaded with those pages ([below](#words-that-load-with-their-pages)) | `settings:appearance.timeZone`, `settings:privacy.showStudyActivity`, `settings:toasts.retry` |
| `servers` | The server dialogs (create a server and its crop, channels and categories, invites, join by code), the invite page and the server settings pages (overview, roles, members, invites, bans). The rail and the channel list use `common`. Loaded with those modules ([below](#words-that-load-with-their-pages)) | `servers:create.title`, `servers:members.noMatch`, `servers:pagination.ofMembers` (with `count`) |
| `deletion` | Deleting an account and restoring it (D-141): the "Delete account" group and dialog on the account page, the sign-in page's `account-deleted` banner, the restore dialog. Loaded with those chunks ([below](#words-that-load-with-their-pages)) | `deletion:confirm.title`, `deletion:banner`, `deletion:restore.description` (with `count`, so `_one` and `_other`) |

A feature has a namespace of its own, so its texts move with it. The `api`
keys are the API's `meta.type` values, looked up for you
([forms-and-errors.md](./auth/forms-and-errors.md)); a success has no
`type`, so its toast is the feature's (`users:toasts.profileUpdated`).

Two parts of `auth` are used outside the auth pages:

- **`auth:sessionEnded.*`**: a session that ended by itself or elsewhere is
  said on the sign-in page, by a banner (`password-changed`,
  `signed-out-everywhere`, `security`, and `ended` for an expired session or
  one signed out from another device). An account waiting to be deleted has
  its banner in `deletion:banner`; the only sign-out toast left, an account
  already deleted, uses `api:AUTH_ACCOUNT_DISABLED`
  (`src/features/auth/lib/sign-out-notice.ts`). The old `auth:signedOut.*`
  and `auth:deleteAccount.*` keys are gone.
- **`auth:signedIn.*`** — the "You're already signed in" card on the
  forgotten- and reset-password pages.

## Words that load with their pages

The namespaces in `src/i18n/index.ts` are in the first download, whichever
page opens. A namespace only some lazy pages use can come with their chunk
instead; `settings` is the first, and the pattern for new page words.
`deletion` follows it: `src/i18n/deletion.ts` is imported by `SignIn`,
`PendingDeletionDialog`, `DeleteAccountSection` and `DeleteAccountDialog`.
So does `servers` (`src/i18n/servers.ts`), the words of the server dialogs
and settings pages, imported by every module of `features/servers` using them.
The steps, with `settings`:

1. The JSON files: `src/i18n/locales/{en,vi}/settings.json`, not listed in
   `resources`.
2. A module that adds them when imported, `src/i18n/settings.ts`:

   ```ts
   export const settingsResources = { en, vi } as const

   i18n.addResourceBundle('en', 'settings', en, true, true)
   i18n.addResourceBundle('vi', 'settings', vi, true, true)
   ```

3. Every module that uses the words imports it for its side effect,
   `import '@/i18n/settings'`: the three pages, `SettingsLoader`,
   `TimeZoneSetting`, `useUpdateSettings` and `useUpdateTimeZone`. Only those modules: imported
   from anything in the first
   download, the words would land there again
   ([code-splitting.md](./code-splitting.md#what-lands-in-the-first-download)).
   Importing it twice is harmless. Every module, not only the first to load:
   a module that relies on another having loaded the words shows raw keys the
   day it loads first (a test renders it alone, a new page imports it).
   `src/i18n/__tests__/page-words.test.ts` reads `src/` (comments left out)
   and names any module using the words of `settings`, `deletion` or
   `servers` without the import: through `useTranslation`, a `servers:`
   prefix, an `ns` option or `<Trans ns>`, `getFixedT`, or a
   `TFunction<'servers'>` handed in. A new namespace loaded with its pages
   goes into its list.
4. `src/i18n/i18next.d.ts` adds the namespace to `defaultNS` and its English
   catalogue to `resources`, so its keys are typed like the others.
5. `src/i18n/__tests__/catalogues.test.ts` compares its Vietnamese keys with
   the English ones too, and checks the words are there once the module is
   imported.

## Errors from the API

The API answers an error with a machine-readable `type` in its envelope, and
that type is the key in the `api` namespace:

```json
{ "meta": { "type": "AUTH_INVALID_CREDENTIALS", "message": "…" } }
```

`getApiErrorMessage(error)` (`src/lib/api-error.ts`) looks up `api:<type>`
and falls back to `api:GENERIC_ERROR`; a request that got no answer is
`api:NETWORK_ERROR`. The API's own `message` is English text for developers
and is never shown. The `AUTH_*` types (wrong credentials, an expired code,
too many attempts…) are all in
`api.json`; the auth pages add their own wording on top
([auth/forms-and-errors.md](./auth/forms-and-errors.md)).

When the API adds an error type, add the key to **both** `en/api.json` and
`vi/api.json`. More: [data-fetching.md](./data-fetching.md#showing-api-errors).

## Typed keys, and the test that keeps the languages equal

- `src/i18n/i18next.d.ts` types `t()` against the English catalogue, every
  namespace included (`settings`, `deletion` and `servers`, loaded with their
  pages, too): a key that
  does not exist in English is a type error,
  caught by `pnpm build` and your editor, instead of a raw key on screen.
- `src/i18n/__tests__/catalogues.test.ts` fails when a namespace's Vietnamese
  keys differ from the English ones, so Vietnamese never silently falls back
  to English.

## The language switch

`<LanguageToggle />` (`src/components/LanguageToggle.tsx`) is at the foot of
the AuthShell, the layout of the sign-in pages: "Tiếng Việt · English",
each language by its own name. The one in use is plain text; the other is a
button. Choosing one also sets `<html lang>` (`src/i18n/index.ts`), which
screen readers and the browser's translate prompt read. The legal pages
(`/terms`, `/privacy`) have a switch in their bar.

Inside the app, the language is the account's, chosen on Appearance &
language (`/settings/appearance`) and saved with the other settings
(`PATCH /users/me/settings`), so it is the same in every browser.
`useAccountSettings()` (`src/features/users/hooks/useAccountSettings.ts`),
mounted once by the AppShell, calls `i18n.changeLanguage()` with it as the
app opens, when the page changes it, and when another tab saves it. The
browser's copy (`i18nextLng`) is updated too, for the pages outside the app
and the next load.

The switch can be used while a message is on screen. On `/register`,
`/verify` and `/welcome`, every message is kept as a key and put into words
when shown, so it changes language with the page
([auth/forms-and-errors.md](./auth/forms-and-errors.md#messages-kept-as-keys)).
The older auth pages still keep the words they had when the message arrived.

**The language on screen also goes to the API.** `currentLanguage()` in
`src/i18n/index.ts` names it as the API does (`vi` or `en`). Every request
that makes the API send an email carries it as `language`, so the email reads
like the page that asked for it, and "complete your account" saves it as the
account's language (`src/features/auth/api/auth.api.ts`).

## Adding a language

Japanese (`ja`) as the example:

1. Copy `src/i18n/locales/en/` to `src/i18n/locales/ja/` and translate the
   eight files. `settings.json`, `deletion.json` and `servers.json` are added
   in `src/i18n/settings.ts`, `src/i18n/deletion.ts` and `src/i18n/servers.ts`
   (`addResourceBundle('ja', 'settings', ja, true, true)`), not in
   `resources`.
2. In `src/i18n/index.ts`, import them and add the language to `resources`
   **and** to `supportedLngs`:

   ```ts
   import jaCommon from './locales/ja/common.json'
   import jaPages from './locales/ja/pages.json'
   import jaApi from './locales/ja/api.json'
   import jaAuth from './locales/ja/auth.json'
   import jaUsers from './locales/ja/users.json'

   export const resources = {
       // ...en, vi
       ja: { common: jaCommon, pages: jaPages, api: jaApi, auth: jaAuth, users: jaUsers }
   } as const

   // in init():
   supportedLngs: ['en', 'vi', 'ja'],
   ```

   Without it in `supportedLngs`, a browser set to Japanese still gets the
   fallback.
3. Add it to the list in `src/components/LanguageToggle.tsx`, by its own
   name (the Appearance page's language choice reads the same list):

   ```ts
   export const LANGUAGE_NAMES = [
       // ...existing
       { code: 'ja', name: '日本語' }
   ] as const
   ```

4. Extend `src/i18n/__tests__/catalogues.test.ts` so it compares `ja` with
   `en` too: today it compares `vi` only.
5. The account's language is stored by the API, which knows `vi` and `en`
   only (`LANGUAGES` in its `user-settings.rules.ts`): add `ja` there too, or
   saving it on the Appearance page is refused.

## Which language a visitor gets

The choice is remembered in `localStorage` (`i18nextLng`). On a first visit,
the browser's language decides; a language the app does not have falls back
to English.
